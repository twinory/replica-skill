Blocked before the paint

Filter rules become native content blockers: a WKContentRuleList on iPhone, request interception on Android. The ad request never reaches the page, so there is no empty box to cover up later.

⤢

One tap to App view

Chrome slides away, the status bar stays, safe areas are respected, and per site CSS removes the web-only banners. The page is not reloaded, so nothing is lost.

⚙

One codebase, two engines

Flutter around WKWebView on iPhone and Android WebView on Android. Same app, same filters, same behaviour. Native engines mean no engine to rebuild and no Safari licence to fight.

What it will not do

Every ad-free browser on the store over-promises, then gets blamed for the first pre-roll. This is the list the app shows on its own settings screen.

Ads baked into the video stream When the ad is in the same file as the show, there is nothing to block. Most YouTube pre-rolls, Twitch and live sport. The player patch skips what it can.
Spotify and Netflix on iPhone Their web players need Widevine. Apple does not expose it to apps. Android usually works. Veil offers the real app instead of a black screen.
Google sign-in inside the page Google refuses its login page in any embedded web view. That one page opens in the system browser and the session comes back.
Promoted posts with no marker Served from the same endpoint as real posts, wrapped in nothing. Rules catch the ones with a wrapper. The rest need a human.

Yours, on your Worker

The app never phones home to someone else's server. Filters and App view patches come from a Worker you deploy, so a broken selector can be fixed without a store review.

cd browser/deploy
npm install
npm run dev      # local Worker with the landing page, demo and /v1 endpoints
npm run deploy   # syncs filters and patches, then publishes to your account

curl https://your-worker.workers.dev/v1/manifest.json

Endpoints: /v1/manifest.json, /v1/patches.json, /v1/filters/base.txt, /health. All static, all cacheable, no database.
